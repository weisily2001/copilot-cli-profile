# Copilot CLI 配置同步到 GitHub 仓库设计

## 问题

当前 `C:\Users\HP\.copilot` 已积累出一套可运行的 Copilot CLI 配置、脚本、模板、技能和说明文档，但这些内容还没有进入一个可跨主机同步、可走 PR、可回滚的远端 GitHub 仓库。现在的本地仓库只有初始化提交，绝大多数稳定配置仍是未跟踪状态。

目标是把这套最近验证过的配置整理成一个公开仓库，便于在不同主机上复用，并支持后续更新、PR 审阅、版本标签和回滚。

## 目标

- 将当前 `.copilot` 目录整理为可公开同步的配置仓库。
- 仅同步稳定内容，包括配置、脚本、模板、技能、文档和可复用规则。
- 排除运行态、主机态和临时产物，避免公开仓库混入噪音和环境耦合内容。
- 为后续跨主机拉取、分支开发、PR 审阅和标签回滚建立清晰流程。

## 非目标

- 不把 `logs`、`session-state`、指标 JSONL、缓存和其他运行态产物纳入公开仓库。
- 不把每台机器的临时状态、当前会话噪音或一次性实验数据当成长期配置同步。
- 不在这次工作里设计新的配置体系，只整理并同步已经验证有效的现有内容。

## 推荐方案

采用单仓库方案，仓库名为 `copilot-cli-profile`，直接以当前 `C:\Users\HP\.copilot` 作为仓库根目录继续整理和发布。

这样可以最大化复用当前目录结构，避免做二次搬迁。后续跨主机只需要克隆仓库或拉取更新。配置变更可以通过分支和 PR 管理，稳定状态可以通过标签固化，出问题时可以快速回滚。

## 内容边界

### 纳入版本库的内容

- 稳定配置文件，如 `config.json`、`settings.json`、`mcp-config.json`、`lsp-config.json`、`copilot-instructions.md`
- 可复用脚本和诊断工具，如 `hooks`、`diagnostics`
- 可复用技能、代理和模板，如 `skills`、`agents`、`templates`
- 设计文档、实施计划、说明文档和长期治理文档
- 可跨会话复用的长期记忆规则和偏好文件

### 排除的内容

- `logs`
- `session-state`
- `hook-metrics.jsonl`
- `startup-metrics.jsonl`
- 其他缓存、临时文件、一次性运行产物和主机耦合内容

## Git 结构与发布策略

`main` 作为稳定分支，先承载这次整理后的基线版本。

每次完成一轮经过验证的配置更新后，在 `main` 上打标签，作为可回滚的最佳状态。后续改动走特性分支和 PR，合入后再视情况打新标签。

这样既保留了单机快速使用的简单性，也具备远端协作和版本回退能力。

## 执行流程

1. 清理版本边界，补充 `.gitignore`，明确哪些目录和文件属于稳定配置，哪些属于运行态噪音。
2. 检查当前未跟踪内容，将稳定配置分批纳入版本库。
3. 以清晰提交历史固化当前已验证配置。
4. 在 GitHub 上创建公开仓库 `copilot-cli-profile`。
5. 为本地仓库添加远端并推送 `main`。
6. 在首个稳定节点打标签，作为跨主机同步和回滚基线。

## 跨主机使用方式

新主机以仓库为配置源。通过克隆仓库获取配置，通过拉取 `main` 获取稳定更新，通过切换标签或回退提交恢复到最佳状态。

需要试验新配置时，在本地新建分支，验证通过后再发起 PR 或合并回 `main`。

## 风险与处理

公开仓库最主要的风险是把运行态或主机态内容误同步上去。处理方式是先收紧 `.gitignore`，再逐项检查纳入版本库的文件。

另一个风险是提交历史过于粗糙，影响后续回滚。处理方式是按内容边界分批提交，保证每个提交都可读、可解释。

GitHub 远端创建和首次推送依赖当前环境是否已有可用登录态或 token。如果缺少这一步，本次也至少要把本地仓库整理到可一键推送的状态，只把最小远端连接步骤留到最后。

## 验收标准

- 本地仓库能清楚区分稳定内容和运行态内容。
- 最近有效的 Copilot CLI 配置被纳入 Git 版本管理。
- 仓库可以推送到公开的 GitHub 仓库 `copilot-cli-profile`。
- `main` 可以作为后续跨主机同步的稳定入口。
- 至少具备一个明确的稳定回滚点。
